# PSFoundation v2: C# implementation migration plan

**Status:** Implementation handoff based on the agreed migration direction **Development branch:** `v2` **Public product:** `PSFoundation`
**Primary repository:** <https://github.com/adnoctem/PSFoundation> **Downstream compatibility reference:**
<https://github.com/adnoctem/winkit>

> PSFoundation v2 replaces the PowerShell implementation with reusable C# libraries and thin compiled PowerShell cmdlets while preserving
> the existing public PowerShell API and its observable behavior.

## 1. Purpose and interpretation

This document is the implementation brief for the coding agent responsible for the v2 migration. It defines the intended architecture,
compatibility obligations, test strategy, development sequence, and completion criteria.

The goal is a complete implementation rewrite of the module. Consumer scripts, particularly those in `winkit`, remain PowerShell and should
continue working without modification. All substantive module functionality moves into dedicated C# services, planners, validators, platform
adapters, and supporting types. The PowerShell-facing C# project exposes the existing commands through thin `PSCmdlet` classes.

This is an implementation migration, not a public API redesign. Later major versions, such as v3 or v4, may deliberately revise the public
API. The fact that this release is called v2 does not grant permission to introduce incidental breaking changes.

The earlier discussion identified Office as a suitable pilot because its configuration, inventory, planning, execution, and verification
responsibilities have natural C# boundaries. Office is the first substantial domain to migrate, not the entire scope of v2.

### 1.1 Authority and evidence

The architecture and compatibility policy in this document are agreed design requirements. Command names, illustrative types, and directory
examples are not an exhaustive extraction of repository contents.

Before implementation, inspect the actual repository, applicable `AGENTS.md` instructions, manifests, exports, tests, help, and downstream
consumers. Pin an exact v1 reference commit and release/package version. That baseline supplies the authoritative command inventory and
behavior. Do not use a moving `main` branch as the oracle throughout the rewrite.

This handoff consolidates the supplied discussion; it does not certify a fresh audit of every current repository file. Where examples differ
from the pinned baseline, preserve the actual baseline and record the discrepancy. Do not invent commands or parameters to make an example
fit.

Use **must** for release requirements, **should** for the preferred implementation approach, and **may** for optional choices. Resolve
routine internal choices autonomously within these requirements. Escalate genuine public-contract conflicts with concrete evidence and a
proposed resolution.

## 2. Agreed decisions

| Area                  | Decision                                                                                              |
| --------------------- | ----------------------------------------------------------------------------------------------------- |
| Product               | Continue publishing one `PSFoundation` PowerShell module.                                             |
| Implementation        | Move all substantive module implementation into C#.                                                   |
| PowerShell interface  | Use thin compiled `PSCmdlet` adapters that preserve the current public API.                           |
| Consumers             | Keep existing PowerShell scripts, including `winkit`, unchanged.                                      |
| Branching             | Develop the rewrite on `v2`; retain the v1 implementation as the comparison baseline.                 |
| Architecture          | Separate domain libraries from the PowerShell adapter assembly.                                       |
| Internal organization | Organize projects by domain and larger domains by feature/responsibility.                             |
| First domain          | Use Office as the pilot; migrate remaining domains incrementally.                                     |
| Testing               | Make C# tests the primary implementation suite; retain PowerShell contract and selected E2E tests.    |
| Compatibility         | Compare v2 with a pinned v1 baseline through metadata and behavioral fixtures.                        |
| Runtime direction     | Retain Windows PowerShell 5.1 and PowerShell 7 compatibility, with an explicit tested version matrix. |
| Future API changes    | Record proposals for later majors without implementing them as part of this rewrite.                  |
| Reuse                 | Domain assemblies must be usable from ordinary C# applications without the PowerShell adapter.        |

## 3. Scope and non-goals

### 3.1 In scope

- Inventory all public commands, aliases, parameter contracts, outputs, and observable behavior.
- Port functionality from all existing source domains into responsibility-focused C# components.
- Introduce typed internal models, action enums, validation results, exceptions, and platform boundaries.
- Preserve PowerShell binding, output, stream, error, confirmation, and pipeline behavior through adapters.
- Build a reproducible binary module package under the existing public module identity.
- Preserve help, discoverability, formatting, dependency handling, and established platform behavior.
- Retain and strengthen existing safety properties, especially around Office deployment and external processes.
- Establish C# unit/integration tests, PowerShell compatibility tests, and selected real-environment tests.
- Document the architecture and the evidence supporting compatibility.

### 3.2 Out of scope

- Renaming commands, aliases, parameters, or parameter sets.
- Redesigning output shapes or replacing accepted inputs with a narrower contract.
- Requiring downstream scripts to adopt new calling patterns.
- Splitting the public product into independently versioned Gallery modules.
- Building the future GUI, CLI, HTTP API, or interactive automation agent.
- Adding features merely because the new architecture makes them convenient.
- Removing Windows PowerShell 5.1 support as an incidental implementation shortcut.
- Promising new operating-system or architecture support that v1 did not have.
- Introducing speculative infrastructure, a plugin framework, or universal abstraction layers.

Internal architecture may improve substantially. Observable semantics remain constrained by the compatibility baseline.

## 4. Definition of compatibility

“1:1 replacement” means that supported existing invocations continue to bind and produce equivalent observable results, side effects,
streams, and failures in the supported environments.

The switch from script functions to compiled cmdlets necessarily changes implementation metadata such as `CommandType`, implementing
assembly, and the availability of a script block. These are deliberate consequences of the agreed architecture. Record them in an explicit
compatibility allowlist; never ignore all metadata differences as a group.

### 4.1 Command and binding contract

Capture and preserve, where present:

| Contract area      | Required comparison                                                                               |
| ------------------ | ------------------------------------------------------------------------------------------------- |
| Command identity   | Exported names, aliases, module identity, and module-qualified invocation.                        |
| Parameter identity | Names, aliases, declared types, and discoverable metadata.                                        |
| Parameter sets     | Set names, membership, default set, mandatory status, and position per set.                       |
| Binding            | Pipeline-by-value, pipeline-by-property-name, remaining arguments, and conversions.               |
| Validation         | Validate sets/ranges/patterns/scripts, null/empty handling, and validation timing.                |
| Defaults           | Omitted versus explicitly supplied values, including `$null` and `$false`.                        |
| Switches           | Omitted, enabled, and explicitly disabled forms such as `-Force:$false`.                          |
| Common parameters  | Existing advanced-function behavior and applicable common parameters.                             |
| Confirmation       | `SupportsShouldProcess`, `ConfirmImpact`, prompts, `-WhatIf`, and `-Confirm`.                     |
| Dynamic behavior   | Dynamic parameters, argument completion, provider paths, and scope-sensitive behavior where used. |

Do not replace a public string parameter with an enum solely because the internal implementation uses an enum. That can change accepted
inputs, conversion behavior, validation, and error messages. Keep the public contract and translate to an enum inside the adapter or a
boundary converter.

Defaults that depend on the current location, environment, or invocation state must retain their evaluation timing. A field initializer
evaluated during cmdlet construction is not automatically equivalent to a PowerShell parameter default evaluated during binding.

### 4.2 Output contract

Preserve object cardinality, ordering, property names, property types, nested shapes, nulls, empty collections, and collection enumeration
behavior. Include custom type names, attached members, formatting, and serialization behavior where the baseline or consumers rely on them.

Typed C# objects are encouraged internally. They are not automatically compatible replacements for public `PSCustomObject` values. Records
may change mutability, equality, property accessibility, type identity, or serialization.

Use an explicit output mapper in `PSFoundation.PowerShell` where required. It may construct `PSObject` instances and existing
property/type-name shapes while domain code remains strongly typed. Preserve object identity or mutability where a supported workflow
depends on it. If an existing command returns a live native/COM object, isolate any necessary compatibility exposure at the boundary and
document ownership; do not silently replace it with a snapshot.

Pay particular attention to `WriteObject(value)` versus `WriteObject(value, enumerateCollection: true)`. Test zero, one, and many results.
No diagnostic text, child-process output, or incidental return value may leak onto the success stream.

### 4.3 Errors and streams

Capture error category, error identifier, exception behavior, target object, exception data, and terminating versus non-terminating
semantics. Include `-ErrorAction Stop`, continuation after a failed pipeline item, and partial output before failure.

Preserve meaningful verbose, warning, information, debug, progress, and host interactions. Do not replace `Write-Host` with `Write-Verbose`,
or move warnings into ordinary output, merely for stylistic consistency. If a host interaction exists, provide a PowerShell-free host
abstraction to the service when necessary and implement it in the adapter.

Error-message fidelity should follow actual dependencies and baseline tests. Do not discard identifiers or categories because text appears
similar. Conversely, localized host-generated text may need structured assertions rather than byte-for-byte snapshots.

### 4.4 Side effects and environmental behavior

Preserve mutation targets, operation ordering, exit-code interpretation, cleanup behavior, working-directory behavior, registry views,
encoding, file formats, and path semantics relevant to the command.

Provider-qualified PowerShell paths and ordinary filesystem paths are not interchangeable. Resolve PowerShell provider semantics at the
adapter boundary where required, and pass explicit filesystem paths to services. Characterize relative paths, wildcard expansion, and
literal-path behavior before porting them.

The same applies to external tools and built-in PowerShell capabilities: replacing an invocation with a .NET API is acceptable only when its
relevant behavior remains equivalent.

### 4.5 Existing quirks and justified exceptions

Retain awkward but intentional or established behavior during v2. Label compatibility code and link it to a fixture and a possible
future-major issue.

Do not reproduce a demonstrated security defect blindly. A proposed exception must identify the old behavior, affected commands, concrete
risk, chosen replacement, downstream impact, regression tests, and maintainer approval. A perceived cleanup opportunity is not an approved
exception.

Maintain an exception ledger with no unreviewed entries at release. Do not silently refresh baseline snapshots to make v2 pass.

## 5. Target architecture

> Registry refinement approved 2026-10-04: build a coherent public C# registry API for other applications, beyond the existing PowerShell
> command surface. Preserve PowerShell compatibility separately. Follow [reusable API boundaries](docs/decisions/reusable-library-api.md)
> and the [registry API contract](docs/registry-api.md). This targeted expansion supersedes the compatibility-only feature restriction for
> registry; it does not authorize the remaining domains in the current checkpoint.

### 5.1 Dependency direction

The existing PowerShell scripts invoke `PSFoundation.PowerShell`. That assembly binds parameters and calls C# domain components. Domain
components use narrow platform abstractions whose implementations access Windows, files, registry, processes, network services, and COM as
needed.

Future C# applications may reference the same domain assemblies directly.

| Layer                     | Owns                                                                                                    | Must not own                                                                              |
| ------------------------- | ------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `PSFoundation.PowerShell` | Public command contract, PowerShell binding, streams, confirmation, compatibility mapping, composition. | Deployment policy, parsing algorithms, inventory rules, or substantive native operations. |
| Domain libraries          | Services, planning, normalization, validation, domain workflows, typed results.                         | `PSCmdlet`, `PSObject`, runspaces, or PowerShell error/stream types.                      |
| Platform components       | Registry, filesystem, process, signature, network, native and COM integrations.                         | PowerShell API policy or duplicated domain decisions.                                     |
| `PSFoundation.Core`       | Small, demonstrably shared abstractions and primitives.                                                 | An accumulation of unrelated helpers or dependencies back to domain projects.             |

No production domain library may directly or transitively reference `System.Management.Automation`, `PSFoundation.PowerShell`, or the
PowerShell SDK. The reusable implementation must not execute embedded PowerShell or launch `powershell.exe`/`pwsh.exe` to perform its own
migrated business logic.

If a domain depends on a capability available only through an existing PowerShell module, identify that dependency early. Investigate
native/.NET alternatives. Any unavoidable host-specific integration requires a documented boundary and resolution; hiding the old script
behind a C# wrapper does not complete the migration.

### 5.3 Service boundaries

Services represent responsibilities, not a mechanical one-service-per-command mapping. Several Office cmdlets may use one planner and one
executor. Avoid both `InstallOfficeService`/`UpdateOfficeService` duplication and a single enormous `OfficeService`.

Prefer explicit dependencies and constructor injection. A small composition root in the adapter may construct production services; a
dependency-injection container is optional. Do not impose a generic host or service locator on all consumers.

Keep command-specific mapping in the adapters and reusable orchestration in domain components. Complex multi-step business workflows must
not gradually migrate back into `ProcessRecord`.

## 6. Runtime and dependency strategy

### 6.1 Supported hosts

The working compatibility target is Windows PowerShell 5.1 plus PowerShell 7. During baseline discovery, record exact minimum/tested
PowerShell versions, Windows versions, .NET prerequisites, processor architectures, and existing non-Windows behavior. Do not interpret “7+”
as evidence that every release has been tested.

Reconcile legacy `#Requires -Version 5.0` statements with manifests and published support claims. The proposed floor is 5.1. If the actual
public contract includes 5.0, document and resolve that conflict rather than silently dropping it.

### 6.2 Starting implementation approach

Microsoft documents `netstandard2.0` and `PowerShellStandard.Library` as an approach for binary modules spanning Windows PowerShell and
modern PowerShell. Start with that approach for the adapter where feasible, and verify the full dependency graph in both hosts. Targeting
.NET Standard does not prove all platform APIs work at runtime. See [R1].

Use compatible targets for domain libraries loaded by that adapter. If real platform dependencies prevent a shared binary, multi-target the
affected components and select the correct assembly set with a minimal loader. Record the evidence and packaging consequences in an
architecture decision.

Do not load a modern-.NET-only assembly into Windows PowerShell 5.1, and do not assume a `netstandard2.0` adapter makes incompatible
transitive dependencies portable. Keep the build SDK choice separate from supported runtime requirements.

Language features such as records or `required` members must be checked against target-framework and tooling requirements. Use ordinary
classes where simpler. The desired architecture does not depend on a particular C# syntax feature.

### 6.3 Dependency policy

- Pin the SDK and package versions using repository conventions and reproducible restore practices.
- Select versions that support the agreed targets; record decisions rather than using floating “latest” versions.
- Keep the PowerShell reference package a build-time dependency and verify it does not cause the package to ship a competing PowerShell
  runtime.
- Audit transitive assets in the produced module, including native dependencies and architecture-specific binaries.
- Exercise real host loading and dependency-conflict scenarios. Compilation and direct DLL tests are insufficient.
- Keep dependencies proportional to demonstrated needs.

## 7. PowerShell adapter design

### 7.1 One discoverable class per command

Use predictable mappings such as `Get-OfficeInventory` to `GetOfficeInventoryCommand.cs`, grouped by the existing source domain.

An adapter generally owns parameter declarations, binding-to-domain conversion, service invocation, confirmation integration, result
mapping, stream translation, and error translation. Most classes should remain small, but file length is not an acceptance criterion;
correct behavior is.

A shared base class may centralize lifecycle, cancellation, or error helpers. Avoid a framework with opaque behavior that makes individual
command compatibility hard to inspect.

### 7.2 Lifecycle and per-record behavior

Respect the distinction between `BeginProcessing`, `ProcessRecord`, `EndProcessing`, and `StopProcessing`. Test multiple pipeline items so
defaults, input values, resources, and failures do not leak between records.

Use invocation-bound parameter information where required to distinguish omitted parameters from explicitly supplied defaults. Do not
collapse these states prematurely into a domain DTO.

Dispose owned resources on success, failure, and cancellation. Do not rely solely on `EndProcessing` for cleanup that must occur when the
pipeline is stopped; verify the lifecycle facilities available in each supported host.

### 7.3 Confirmation and dry-run behavior

PowerShell owns `ShouldProcess` and host prompting. Domain code owns eligibility and operation safety. Neither substitutes for the other.

Characterize the existing confirmation boundary and reproduce its targets, actions, scope, and observable preparation behavior. Generally,
gather the read-only information required to describe the operation, obtain approval, revalidate as necessary, and then execute.

No deployment, deletion, configuration write, or other mutation governed by the command may occur when `ShouldProcess` declines it. Inspect
preparation carefully: downloads, directory creation, generated XML, and cache writes can also be observable mutations. If v1 behaves
unexpectedly under `-WhatIf`, characterize it and resolve any safety correction through the exception process.

For workflows requiring multiple confirmations, use a narrow domain-neutral authorization callback or staged operations. Do not pass a
`PSCmdlet` into the service or let the adapter reimplement the business workflow.

Do not change the number of prompts, confirmation granularity, or `-Force` interactions accidentally. Document expected output under
`-WhatIf`; returning nothing is not automatically compatible.

### 7.4 Progress, diagnostics, and cancellation

Services may accept `IProgress<T>`, structured diagnostic callbacks, and `CancellationToken`. They must not call PowerShell stream APIs.

**Correction to an earlier illustrative snippet:** do not blindly construct `new Progress<T>(p => WriteProgress(...))` inside a cmdlet.
`Progress<T>` dispatches through its captured synchronization context or the thread pool, while `WriteProgress` must run on the active
cmdlet lifecycle thread. See [R2] and [R3].

Choose one explicit execution model:

- For synchronous services that report on the calling thread, use an inline `IProgress<T>` implementation with a documented same-thread
  contract.
- For worker or asynchronous operations, enqueue progress, diagnostics, and results; drain them on the pipeline thread while the cmdlet
  lifecycle method remains active.

The second model needs bounded buffering or progress coalescing, deterministic completion, cancellation, and exception propagation. An
inline callback does not solve cross-thread reporting if the service itself invokes it from a worker.

Keep all `WriteObject`, `WriteError`, `WriteWarning`, and related host interactions on the appropriate pipeline execution path. Do not use
`async void` lifecycle overrides or write streams from `StopProcessing`.

Connect `StopProcessing` to a thread-safe cancellation request. Observe cancellation at safe points. Define behavior for an external
deployment process already running; stopping a PowerShell pipeline does not imply that killing an installer is safe. Do not report success
for a cancelled or partially completed operation. Preserve the baseline's observable result/error behavior while keeping internal
cancellation explicit.

### 7.5 Error translation

Use domain-specific exceptions or result types carrying meaningful reason codes. Keep `ErrorRecord`, `ErrorCategory`, and PowerShell
termination policy in the adapter.

Maintain an explicit mapping from domain failures to the legacy error surface. For Office, preserve `Exception.Data['OfficeReason']` where
the baseline or consumers use it, even if the internal implementation also has a typed reason enum.

Do not map every exception to a terminating error. Preserve partial failure and per-item continuation where required. Preserve useful inner
exceptions and avoid replacing detailed causes with a generic message.

Pipeline-stopped exceptions must not be swallowed and converted into ordinary operational failures. Allow stopping to unwind correctly while
performing safe cleanup.

## 8. Domain implementation and platform boundaries

### 8.1 Typed internal contracts

Use explicit types for configuration, inventory, plans, results, progress, and failure reasons. Represent uncertainty separately from known
absence and confirmed compliance.

Types eliminate some invalid states; they do not replace runtime validation of external input, registry content, files, deserialized
objects, or execution authority. Constructors and boundary converters should make required invariants clear.

Prefer immutable plans and snapshots where useful. A returned plan remains untrusted input at execution time even if its C# type is
immutable: it may be stale, externally constructed, or mapped from a legacy PowerShell object.

### 8.2 Platform abstractions

Introduce interfaces where they isolate side effects or enable meaningful tests. Examples include a registry snapshot reader, process
runner, signature verifier, filesystem operations needed by a workflow, and clock when time affects behavior.

Do not reproduce the entire operating system as one huge `IFileSystem` or create an interface for every pure class. Use the narrowest useful
boundary.

Platform implementations must specify ownership and behavior: registry view, process arguments, working directory, environment, timeout,
cancellation, output capture, exit code, and cleanup. Test command-line quoting and paths with spaces. Avoid shell command construction
where direct invocation is available.

Pure parsers should consume snapshots or bytes rather than reading machine state internally. Use representative fixtures and concrete
platform integration tests to ensure fakes do not conceal real differences.

### 8.3 Reuse and architecture enforcement

Add an automated dependency check that production domain assemblies do not depend on PowerShell. Include a small C# consumption test that
creates a service and performs a pure operation without a PowerShell host.

Do not make public C# library design a second large redesign project. Expose coherent operations needed by the migration and future reuse,
and retain flexibility in internal implementation details.

## 9. Office pilot design

### 9.1 Responsibility map

The following names are proposed internal components, not additional public PowerShell commands.

| Component                      | Responsibility                                                                |
| ------------------------------ | ----------------------------------------------------------------------------- |
| `OfficeInventoryService`       | Acquire relevant observations and build inventory.                            |
| `OfficeRegistryParser`         | Interpret registry snapshots, product state, and uncertainty.                 |
| `OfficeAppPathResolver`        | Resolve application paths according to established rules.                     |
| `OfficeConfigurationFactory`   | Normalize accepted boundary inputs into a typed configuration.                |
| `OfficeConfigurationValidator` | Validate product, channel, language, application, and option combinations.    |
| `OfficeDeploymentPlanner`      | Produce a plan from an action, desired configuration, inventory, and options. |
| `OfficeDeploymentExecutor`     | Revalidate and coordinate an authorized deployment workflow.                  |
| `OfficeComplianceVerifier`     | Compare observed state with the required post-operation state.                |
| `OfficeMediaService`           | Coordinate media acquisition and preparation.                                 |
| `OfficeMediaValidator`         | Check manifests, files, hashes, and applicable media constraints.             |
| `OdtConfigurationBuilder`      | Generate Office Deployment Tool XML from validated inputs.                    |
| `OdtClient`                    | Validate and invoke the deployment tool and interpret its result.             |

The earlier discussion named actions such as Install, Remove, Migrate, Update, SetUpdateConfiguration, AddLanguage, RemoveLanguage,
SetApplicationSelection, and SetApplicationPreference. Verify the exact set against the pinned source and preserve its accepted public
values. An internal `OfficeDeploymentAction` enum is appropriate after boundary conversion.

### 9.2 Planning and execution

Keep planning as pure as practical: explicit inventory and configuration in, deterministic plan out. Offline planning must not silently
access the live registry or start external processes.

Execution must obtain or verify current machine state and recheck safety and eligibility. An inventory supplied for planning must not be
treated as trusted execution authority. Preserve fingerprints and stale-plan handling according to the baseline.

The intended workflow is observation, configuration normalization, planning, authorization, execution-time revalidation, mutation, fresh
observation, and compliance verification. Preserve the exact placement of existing safety checks and cleanup obligations where it affects
behavior.

Do not treat successful process exit as proof that the desired Office state was achieved. Return or report the established discrepancy and
unknown-state information after verification.

### 9.3 XML and media behavior

Make ODT XML generation a deterministic, separately tested component. Use structured XML APIs and explicit handling for optional attributes
and ordering where required.

Use reviewed golden fixtures for the actual supported cases, including representative installation, pinned updates, language
addition/removal, application exclusions, and product migration scenarios. The earlier examples included LTSC 2024 with `de-DE`/`en-US` and
Microsoft 365-to-LTSC migration; validate product identifiers and supported combinations against the pinned implementation before creating
fixtures.

Compare XML semantically where formatting is irrelevant. Preserve exact bytes where hashes, manifests, or consumer behavior depend on them.
Never normalize away a meaningful product, channel, language, action, or removal target.

### 9.4 Safety properties to preserve

Verify the protections described in the discussion against the source and port their actual behavior:

- Tool signature and identity verification before execution.
- Media identity, completeness, manifest, and integrity checks.
- Protected-path validation before destructive cleanup.
- Distinction between unknown inventory, absent products, and noncompliance.
- Execution-time eligibility and authority validation.
- Secret-safe handling of product keys and temporary configuration files.
- Cleanup failures reported according to the existing contract.

Retain `SecureString` at the public boundary if that is the existing parameter type. Minimize plaintext lifetime, restrict temporary-file
access, avoid logging secrets, and clear owned unmanaged buffers. Do not promise that managed strings can be reliably erased from memory.

Generate secret-bearing XML only when needed. Test cleanup on success, failure, and cancellation. A cleanup exception must not silently
overwrite the original operational failure or be reported as success; preserve both pieces of information through the established contract.

### 9.5 Office deployment versus Office COM automation

Office installation through ODT and desktop Office automation through COM are different execution environments. Do not impose
interactive-desktop constraints on ordinary deployment operations merely because both concern Office.

For COM-facing functionality actually present in the module, define apartment ownership and object lifetime. The Office object model is not
thread-safe and uses STA serialization; adding C# does not make unrestricted parallel calls safe. See [R4].

Keep native objects inside the owning platform/session layer whenever the legacy contract permits. Do not blindly call
`FinalReleaseComObject` on shared objects, force garbage collection as routine cleanup, or send COM objects through generic worker queues.
Test disposal and error paths against actual supported hosts.

Future desktop or API-agent consumers are architectural possibilities, not v2 deliverables. Their hosting models need separate assessment
before reusing interactive COM automation in unattended services.

## 10. Testing strategy

### 10.1 Test responsibilities

Use xUnit as the preferred C# test framework, selecting a version and runners compatible with the chosen runtime matrix. If the repository
has an established equivalent, record a deliberate decision before replacing it.

| Suite                          | Primary purpose                                                                     | Typical environment                                                         |
| ------------------------------ | ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| C# unit tests                  | Parsing, normalization, planning, XML, fingerprints, compliance, and failure rules. | Deterministic fixtures; no Office, admin rights, or live registry required. |
| C# integration tests           | Real platform adapters and their boundary contracts.                                | Windows, temporary resources, controlled external-process fixtures.         |
| C# adapter tests               | Complex mapping and lifecycle helpers where direct tests add value.                 | Appropriate PowerShell runtime when needed.                                 |
| Pester API tests               | Exports, parameter metadata, binding, output shape, errors, and streams.            | Separate real `powershell.exe`/`pwsh.exe` processes.                        |
| Pester compatibility scenarios | v1/v2 behavior and unchanged downstream invocation patterns.                        | Controlled fixtures and isolated hosts.                                     |
| Real E2E tests                 | Selected installation, mutation, COM, and recovery workflows.                       | Disposable or explicitly designated Windows test environments.              |

Most implementation tests should be C#. Do not turn the earlier approximate “90%” discussion into a coverage quota. Test distribution
follows behavioral risk and clear ownership.

C# can also host PowerShell runspaces and test binding. Pester is retained because it is an effective, readable consumer-level harness, not
because C# is technically incapable of testing the PowerShell engine. Metadata assertions alone do not prove binding works.

### 10.2 Baseline capture

Before porting production commands, create a repeatable exporter and fixtures for the pinned v1 module. Capture command metadata in each
supported host where it may differ.

Use `Get-Command`, parameter-set/parameter metadata, applicable attributes, and `CommandMetadata` where appropriate. Do not assume every
metadata member is exposed identically on `FunctionInfo` and `CmdletInfo`. Runtime defaults, output shape, and behavioral validation need
invocation tests in addition to reflection.

Commit sanitized baseline fixtures, their source commit/package identity, host versions, and capture instructions. Review their initial
contents. An empty fixture or one generated from v2 cannot establish backward compatibility.

### 10.3 Golden-master comparisons

Run v1 and v2 against equivalent inputs and controlled environmental snapshots, using separate processes and explicit module paths. Avoid
command shadowing and assembly collisions from loading both versions into one process.

For Office planning, compare action, eligibility, blockers, warnings, products, languages, removal targets, normalized settings, and all
other contractually relevant fields.

Normalize only documented nondeterminism: generated timestamps, fixture-specific temporary roots, transient process identifiers, or
genuinely random IDs. Preserve relationships between IDs when meaningful. Do not normalize fingerprints, collection ordering, paths, or
unknown-state indicators merely because v2 differs.

JSON alone is insufficient to prove PowerShell object compatibility because it can lose type, null, and cardinality information. Combine
normalized value fixtures with explicit type/property/cardinality assertions and actual invocation tests.

### 10.4 Required behavioral cases

- Omitted, explicit null, empty, whitespace, and explicit false values where accepted or rejected.
- Named, positional, aliased, and splatted invocations.
- All parameter sets and invalid combinations.
- Pipeline binding by value and by property name.
- Zero, one, and many inputs/outputs, including nested collections.
- Confirmation accepted/declined, `-WhatIf`, and existing `-Force` behavior.
- Terminating and non-terminating errors, `-ErrorAction Stop`, and continued processing.
- Output, verbose, warning, information, and progress routing.
- Cancellation and resource disposal.
- Repeated invocation in one host and import in a clean host.
- Relative paths, spaces, provider paths, registry views, and relevant culture/encoding behavior.
- Existing serialization/deserialization workflows where supported.
- Representative unchanged `winkit` calling patterns.

Cover equivalence classes and risk-relevant combinations rather than attempting an unbounded Cartesian product.

### 10.5 Controlled effects and E2E isolation

Pure tests must never install or remove real Office. Use fake process runners and fixtures for planner/executor policy tests. Use actual
platform integration tests to prove the adapters behave as the fakes claim.

Destructive E2E tests must be opt-in and run in disposable or specifically provisioned environments. For a v1/v2 mutation comparison,
restore the same starting state between runs; do not run v2 against the machine already changed by v1.

Record before/after state, process results, sanitized diagnostics, and cleanup outcomes. Keep secrets and user data out of committed
fixtures.

## 11. Module packaging and developer workflow

Continue supporting the public installation model:

```powershell
Install-Module PSFoundation
Import-Module PSFoundation
```

A shared-binary package may contain the manifest, `PSFoundation.PowerShell.dll`, the domain DLLs, necessary runtime dependencies, help, and
format/type data. Internal assembly separation must not force users to install several new Gallery packages.

Set explicit `CmdletsToExport` and aliases. Preserve existing module identity, including the manifest GUID unless a documented requirement
dictates otherwise. Retain metadata, license, links, and supported help behavior; update version and release notes for v2.

For a pure shared-binary package, the root module can be the cmdlet assembly. Use a small `.psm1` loader only for demonstrated requirements
such as framework-specific assembly selection. It must not contain substantive domain implementation.

Convert script comment-based help to a suitable binary-module help workflow while preserving command documentation and examples. Package any
required `.types.ps1xml` and `.format.ps1xml` files deliberately. Do not change display behavior accidentally through new CLR type names.

Build and test the staged release package, not only assemblies in project output folders. The package must import on a clean machine without
the source checkout or development SDK.

During development, use fresh PowerShell processes for rebuilt binaries; do not assume `Remove-Module` unloads already loaded CLR
assemblies. Keep build artifacts separate from source and version the tooling needed to reproduce them.

## 12. Branch and incremental migration strategy

Create or reuse the `v2` branch from the selected baseline according to repository policy. Do not overwrite an existing branch or unrelated
working changes. Preserve v1 on its existing development/release line.

Incremental development may temporarily combine legacy functions with migrated cmdlets. Each public command must have exactly one
intentional owner in the staged module. Avoid depending on incidental command precedence or load order.

When switching a command to C#, remove or exclude its legacy definition from that package's export/load path, retain comparison access
through the pinned v1 reference, and verify `Get-Command -All` plus module-qualified invocation in clean hosts.

Do not delete a private helper until all remaining legacy callers are accounted for. Use the dependency map to coordinate groups of commands
that share state or internal contracts.

Keep commits and pull requests reviewable: baseline capture, scaffolding, pure components, platform components, adapters, and command
cutovers are useful boundaries. Port behavior first and keep unrelated cleanup separate.

Track v1 fixes that land after the baseline. Evaluate each for a corresponding v2 port and update evidence deliberately. Record the final
upstream reconciliation point before release.

## 13. Implementation phases and exit gates

### Phase 0 — Repository discovery and contract freeze

Work:

1. Read repository instructions, build/release configuration, manifests, source, tests, and help.
2. Pin v1 source and package references and establish the `v2` branch.
3. Inventory every exported command, alias, source domain, private dependency, and external dependency.
4. Inspect `winkit` consumers and catalog representative invocation patterns without changing them.
5. Capture API metadata and initial behavior fixtures in the supported hosts.
6. Record the runtime matrix, known quirks, safety invariants, and exceptions needing decisions.

**Deliverables:** baseline record, command map, initial fixtures, runtime matrix, migration tracker.

**Exit gate:** scope is enumerated; compatibility evidence exists before command replacement; runtime strategy has a concrete feasibility
check.

### Phase 1 — Solution skeleton and packaging proof

Work:

1. Establish the C# solution, build settings, dependency strategy, and initial projects.
2. Add the PowerShell composition root and only the shared adapter helpers currently needed.
3. Establish unit tests, Pester host runners, fixture comparison, and architecture checks.
4. Prove a low-risk existing command can be implemented through a C# service and compiled adapter.
5. Package and import it under the existing module identity in the required hosts.

**Exit gate:** the real staged package imports; the selected command passes its v1 contract; domain code remains independent of PowerShell.

### Phase 2 — Office pure core

Work:

1. Introduce internal configuration, inventory, plan, result, and reason-code types.
2. Port normalization, validation, registry snapshot parsing, planning, fingerprints, and compliance logic.
3. Port deterministic XML and manifest-related logic.
4. Add legacy input/output converters and golden-master fixtures.

**Exit gate:** representative and edge-case planning/configuration results match v1 without live Office or machine mutation.

### Phase 3 — Office platform and execution

Work:

1. Implement registry, process, filesystem, signature, and media integrations required by Office.
2. Port execution-time revalidation, tool identity checks, process-result interpretation, and post-operation verification.
3. Preserve protected paths, secret handling, cleanup, partial failures, and cancellation behavior.
4. Add controlled integration tests and designated E2E workflows.

**Exit gate:** execution and cleanup invariants have evidence; failures and uncertain inventory cannot silently become successful deployment
results.

### Phase 4 — Office cmdlet cutover

Work:

1. Implement every public Office command as a thin compiled adapter.
2. Match binding, parameter sets, streams, errors, confirmation, and output contracts.
3. Route progress and cancellation through the tested pipeline-thread model.
4. Switch command ownership in the staged package and retire unneeded legacy Office implementation.
5. Run unchanged Office-related `winkit` scenarios against v2.

**Exit gate:** all Office commands pass contract and behavior comparisons in the required hosts, with no unresolved compatibility
differences.

### Phase 5 — Remaining domains

Repeat the same discovery-to-cutover sequence for Interop, Networking, Devices, Packages, Data, and every additional domain found in
Phase 0. Order them by dependency and risk; the list above is not an assertion of the complete repository structure.

Reuse proven conventions, but do not force unrelated domains into Office-specific abstractions. Keep migration status per command and per
domain visible.

**Exit gate:** every public command is accounted for and ported; all substantive private implementation is C#; no hidden runtime dependence
on legacy script logic remains.

### Phase 6 — Release candidate validation

Work:

1. Build a clean staged module package and validate the complete host/runtime matrix.
2. Run the full contract, behavior, platform, downstream, and selected E2E suites.
3. Inspect package contents, dependency loading, help, formatting, license, and manifest metadata.
4. Reconcile relevant v1 maintenance fixes and close the compatibility ledger.
5. Complete release notes and maintainer handoff with exact test evidence and limitations.

**Exit gate:** all release criteria in Section 16 are satisfied. Publishing and merging follow repository release policy and the
maintainer's authorization.

## 14. CI and verification requirements

Use a staged pipeline so fast deterministic tests run before environment-dependent checks.

| Gate                 | Required evidence                                                                                            |
| -------------------- | ------------------------------------------------------------------------------------------------------------ |
| Build                | Reproducible restore/build for selected targets; documented warnings policy.                                 |
| Architecture         | No PowerShell dependency in production domain assemblies.                                                    |
| Unit behavior        | Pure/domain suites pass with meaningful assertions.                                                          |
| Platform integration | Registry/files/process/signature boundaries verified on supported Windows environments.                      |
| PowerShell hosts     | Real Windows PowerShell 5.1 and selected PowerShell 7 processes import the staged package and run contracts. |
| Compatibility        | Reviewed v1/v2 differences limited to the explicit allowlist.                                                |
| Consumers            | Representative unchanged downstream invocations pass.                                                        |
| E2E                  | Required destructive/COM scenarios pass in designated environments before release.                           |
| Package              | Only intended exports and dependencies; help and formatting included; clean-machine import succeeds.         |

Run a legacy .NET Framework integration path where needed; tests passing only on modern .NET do not establish Windows PowerShell
compatibility. For architecture-specific native behavior, include each supported architecture or explicitly document unsupported
combinations.

If an execution environment cannot run a required gate, report it as blocked or not run with the exact command/environment needed. Do not
describe Linux-only unit test success as Windows or Office validation.

Measure representative baseline and v2 performance where expensive operations justify it. Treat material regressions as defects to
investigate, but do not pursue speculative optimizations at the cost of compatibility. C# alone does not remove registry, process, network,
or COM overhead.

## 15. Risks and prescribed responses

| Risk                                               | Required response                                                                   |
| -------------------------------------------------- | ----------------------------------------------------------------------------------- |
| CLR models change PowerShell output                | Explicit boundary mapping plus type, shape, mutability, and serialization tests.    |
| String-to-enum conversion narrows inputs           | Preserve public parameter types; convert internally after compatible validation.    |
| Declared runtime support exceeds actual support    | Pin a test matrix and run actual host processes against the packaged module.        |
| Progress callbacks write from a worker thread      | Inline same-thread reporting or a tested pipeline-thread queue.                     |
| `-WhatIf` still performs preparation mutations     | Identify all effects and reproduce or explicitly correct the confirmation boundary. |
| Golden tests bless rewritten behavior              | Generate from pinned v1; review fixture changes separately.                         |
| Normalization conceals semantic drift              | Keep a narrow normalization allowlist with explicit rationale.                      |
| Partial cutover loads two implementations          | Explicit command ownership and clean-host export/precedence tests.                  |
| Services remain thin wrappers around scripts       | Dependency checks, source review, and ordinary C# consumption tests.                |
| Excessive abstractions delay migration             | Add boundaries for actual effects, reuse, or test needs only.                       |
| Stale plans authorize destructive actions          | Fresh observation and execution-time validation.                                    |
| Cleanup or diagnostics expose product keys         | Minimize plaintext, redact diagnostics, restrict files, and test failure paths.     |
| Cancellation leaves ambiguous machine state        | Safe stop policy, truthful partial-state handling, and post-operation evidence.     |
| All-in-one Office class recreates the old monolith | Keep inventory, planning, media, XML, and execution responsibilities separate.      |
| Future redesign enters the rewrite                 | Record a future-major issue; preserve v2 compatibility.                             |

## 16. Definition of done

### 16.1 Per-command completion

- [ ] The command has an authoritative v1 contract and representative behavior fixtures.
- [ ] Its substantive implementation resides in C# services/components.
- [ ] Its adapter preserves names, aliases, parameter sets, validation, defaults, and binding.
- [ ] Output cardinality, shapes, relevant types, and ordering match.
- [ ] Errors, streams, confirmation, and cancellation match or have an approved exception.
- [ ] Required side-effect and cleanup tests pass.
- [ ] The staged package exports exactly the intended implementation.
- [ ] Required hosts and relevant unchanged downstream scenarios pass.
- [ ] Help and formatting remain available.
- [ ] Legacy implementation is excluded or removed when no remaining caller needs it.
- [ ] The command map and migration tracker record evidence and status.

### 16.2 v2 release completion

- [ ] Every public command and alias in the pinned baseline is accounted for.
- [ ] All source domains and substantive private helpers have been migrated.
- [ ] Production domain libraries have no PowerShell dependency.
- [ ] Public commands are compiled adapters with no substantial domain logic.
- [ ] Remaining PowerShell files are limited to permitted loading/packaging, build tooling, tests, and unchanged consumers.
- [ ] A normal C# application can consume the domain implementation directly.
- [ ] API metadata, behavioral fixtures, and downstream compatibility gates pass.
- [ ] Required Windows PowerShell 5.1 and PowerShell 7 package validation is complete.
- [ ] Office safety, cleanup, stale-state, and uncertain-inventory behavior are preserved and tested.
- [ ] Designated E2E workflows have passed in controlled environments.
- [ ] No unreviewed compatibility exceptions or unaccounted commands remain.
- [ ] Relevant v1 fixes have been reconciled.
- [ ] One installable `PSFoundation` module includes the required binaries, help, and metadata.
- [ ] Release notes explain the implementation change without claiming unsupported compatibility.
- [ ] Maintainers receive the package, test evidence, known limitations, and release procedure.

## 17. Coding-agent execution instructions

1. Read this plan and repository instructions in full. Inspect the actual source before adopting example names or signatures.
2. Begin with Phase 0. Establish the reference baseline and compatibility harness before large-scale porting.
3. Maintain a command map containing the old source location, new adapter, new service/component, test evidence, and migration status.
4. Complete vertical slices through services, adapters, packaging, and tests. Do not stop at a solution skeleton or claim an Office-only
   port completes v2.
5. Preserve the full public API and unchanged downstream scripts. Convert between legacy shapes and typed internal models at explicit
   boundaries.
6. Make routine internal decisions without repeated permission requests. Document meaningful architecture choices and expose genuine
   compatibility conflicts for review.
7. Keep production PowerShell-free libraries independently usable and tested. Do not use embedded scripts as a shortcut to the finish line.
8. Report real test results, commands, host versions, skipped gates, and remaining work. Never infer Windows/Office success from a build
   alone.
9. When a future API improvement is discovered, record it for a later major and continue the compatible implementation.
10. Do not publish releases or change downstream repositories merely because the implementation is ready; follow the explicit task
    authorization and repository workflow.

The final implementation handoff should include the completed command map, architecture decisions, compatibility exception ledger, packaged
module, and a verification report tied to exact source and runtime versions.

## 18. Deferred improvements for later majors

Potential later work includes public command rationalization, consistent naming, redesigned parameter sets, richer public CLR output types,
stricter validation, removal of compatibility shims, revised platform support, separate NuGet distribution, and dedicated GUI/CLI/API
consumers.

These are possibilities, not committed v2 tasks. Their eventual scope should follow user needs and evidence from the completed migration.
The intended benefit of v2 is that future PowerShell API changes can often be made in the adapter without reimplementing the underlying
functionality.
